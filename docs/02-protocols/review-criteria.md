# 物理验收标准与打回机制（Review Criteria）

PM 对 `IN_REVIEW` 任务执行物理验收的权威判据。流程骨架（五步验证、查账→验物→记账三步操作）见 `agents/pm/prompt.md` §5 与 `agents/pm/tools.md` §三；状态流转与 `rejection_history` 结构以 `orchestration/state_machine.md` 为准。**本文件回答"什么算通过、什么算不通过、打回需要什么证据"。**

## 一、 通用判定规则（所有角色）

1. **文件存在性**：任务卡 `outputs` 逐一物理存在且非空（0 字节、仅占位 TODO 视为不存在）；路径一律相对项目 `root_dir` 解析。
2. **证据真实性**：测试/校验日志必须是真实落盘文件，含完整执行输出结尾与退出码；提测报告中的日志摘录必须能在落盘文件中原文找到。PM 有权在 `root_dir` 重跑校验命令复核，重跑结果与报告矛盾即打回。
3. **副作用扫描**：公共依赖与配置（package.json、锁文件、pom.xml、requirements.txt、Cargo.toml、CI 配置、共享环境变量等）出现任务卡声明之外的改动，直接不通过；确需改动必须先走变更请求（各角色 prompt 的范围蠕变防护条款），获批后计入任务卡。
4. **契约一致性**：涉及冻结契约的交付物（类型定义、接口实现、Mock、测试断言）必须与 `contracts` 登记表中的冻结版本一致；任何字段/路径/错误码偏离 = REJECTED，争议走变更流程而非现场改判。
5. **口头无效**：无物理产物 + 无日志凭证的"已完成"汇报，不进入验收，直接退回补凭证。
6. **安全与审计缺项即不通过**：交付物触及 `docs/02-protocols/security-baseline.md` 的控制项却缺任一形态的证据（机检日志 / 实现位置 / 运行结果 / 人工判据结论），按未达标项打回；豁免必须逐条有理由，无理由的豁免等同未通过。

## 二、 分角色验收判据

### architect 任务
| 判据 | 通过标准 |
| --- | --- |
| Lint 报告 | `contract_validator` 报告 `LINT PASSED`（0 errors）；WARN 须在交付报告中逐条说明 |
| 指纹一致 | PM 重算契约文件 sha256，须与锁文件、交付报告登记块三方一致 |
| 变更类任务 | 附 `diff.py` 报告；`BREAKING_CHANGE` 须附总架构师决策结论，且已开辟新大版本文件 |
| 安全与审计声明 | 契约含 `securitySchemes` / `x-roles`、每 operation 显式 `security` 与 `x-permissions`、写操作 `x-audit`、敏感字段 `x-sensitive` / `writeOnly`；交付报告"安全与审计声明自检"逐条有事实（`api-contract-spec.md` §八）。权限声明的任何放宽须附总架构师决策结论 |
| DDL/迁移骨架 | 业务表含持久层六大基石字段（`api-contract-spec.md` §五）；主键雪花、禁自增 |
| Mock 样例 | 错误码样例覆盖率 100%（E011 已机器校验）；样例语义完备，无 `"string"`/`0` 占位符 |

### developers 任务（各技术栈通用）
| 判据 | 通过标准 |
| --- | --- |
| 静态门禁 | 对应技术栈静态检查 0 errors（前端 `npm run typecheck`；其余按任务卡指定命令），日志落盘 |
| 单元测试 | Pass 率 100%，真实运行日志落盘（含退出码）；任务卡有覆盖率要求时达标 |
| 交付清单对账 | 提测报告文件清单与任务卡 `outputs` 一致，标注新增/修改；清单外文件计入副作用扫描 |
| 契约映射 | 类型/实现与冻结契约字段一一对应，无手敲漂移 |
| 安全与审计机检 | 交付报告含 `check_security.sh`（后端 S002–S008/S010、前端 F001–F008）与 `check_secrets.sh` 的真实通过输出，**`[INFO]` 取证段一并留存**；脚本重跑结果与报告矛盾即打回 |
| 数据变更机检 | 交付含 `.sql` 或数据源配置时，报告含 `check_db_ops.sh`（D001-D015）的真实通过输出与 `[INFO]` 覆盖范围行，并附填全的变更单（`skills/database-ops/assets/templates/db_change_ticket.md`）。**门禁由开发自跑，PM 按批次抽查重跑**，不是每张卡的前置验收步骤；抽查命中"报告说绿、重跑说红"即整批交付打回 |
| 注释与可读性 | 按 `agents/developers/README.md` 第六节判定：无 emoji/图标/分隔横幅/箭头排版，无复述代码的废话注释，注释与实现一致；命中明显 AI 风格即列入整改清单 |

**frontend-react 附加项**：异步组件四态闭环测试存在且通过；mock 走 axios-mock-adapter 体系（业务代码无 mock 分支）；样式无硬编码 hex/rgba；提测报告含联调切换说明（`VITE_USE_MOCK`）。
**后端附加项**：接口行为与契约错误码定义一致（401/409 等不得以 500 代替）；迁移脚本可重复执行不破坏数据（判据见 `skills/database-ops/`，机检 D004 / D005 / D006）。

### 安全与审计判据（跨角色，脚本查不出的部分）

**脚本查得出**的（拼接 SQL、明文比口令、留存天数、暴露面、审计能力缺失）由 `check_security.sh` / `check_secrets.sh` 卡住，
数据侧的（无 `WHERE` 修数、不幂等迁移、无备份兜底的破坏性语句、缺基石列与租户索引）由 `check_db_ops.sh` 卡住；
**脚本查不出**的按 `docs/02-protocols/security-baseline.md` 走人工判据，验收时逐条要实现位置或运行证据，不接受"按基线实现了"这类口头结论：

| 人工判据 | 通过标准 | 证据形态 |
| --- | --- | --- |
| 口令策略真生效（ID-1） | 弱口令、历史口令复用、超长/超短输入在服务端被拒，不是前端拦了就算 | 交付报告列出校验注解与异常分支位置；QA 用例结果 |
| 登录失败处理真生效（ID-2） | 连续失败触发计数与锁定、Token 过期即拒、登出后旧 Token 不可用 | 计数与锁定的实现位置 + 关键参数取值（参数留白须有总架构师拍板记录） |
| 越权真挡住（AC-5） | 垂直越权（低角色调 admin 接口）与水平越权（改 ID 取他人/他租户数据）都返回契约登记的 403 类错误码，且不泄漏资源是否存在 | 交付报告的租户/属主条件代码位置 + QA 越权用例 |
| 审计覆盖业务全量（AU-1） | 契约每个 `x-audit` 声明都有实现与日志样本；失败分支按声明记录 | 审计事件清单对账（`event_type` → 触发点 → 失败分支）+ 真实审计日志摘录 |
| 脱敏真做到（DP-3） | 运行日志与审计 `detail` 里没有明文口令/Token，手机号等按统一规则打码 | 日志抽样原文 + 脱敏工具调用点 |
| 豁免合理（S0xx / F0xx / D0xx） | 每处 `#nosec:` / `// nosec-fe:` / `-- nosec-db:` / `-- dbops-ignore:` 有具体理由且范围最小；无理由的豁免脚本已按 D015 判失败，有理由但理由与门禁项无关的按未通过处理 | 交付报告的豁免清单 |
| 数据变更可回滚（人工判据） | 破坏性脚本写明备份产物路径与恢复命令，回滚在演练环境跑过；大表变更说明执行窗口与锁影响 | 变更单的"备份与恢复""风险评估"两段原文 + 演练记录 |

### QA 任务
| 判据 | 通过标准 |
| --- | --- |
| 报告制品 | `qa/reports/*.md` 含用例清单、通过率、失败证据（物理路径或日志摘录） |
| 日志制品 | `qa/logs/*.log` 为真实执行输出，含命令、时间戳、退出码，可复现 |
| 路径覆盖 | 正常路径 + 错误路径全覆盖；契约 `x-error-codes` 登记表内错误码 100% 有用例 |
| 独立性 | 用例设计依据冻结契约而非实现代码；发现实现与契约冲突时报告事实，不现场裁定 |
| 安全用例 | 越权（垂直 + 水平）、鉴权绕过（未带 Token / 伪造身份）、登录失败锁定、脱敏与审计覆盖：以契约 `x-permissions` / `x-audit` 为基准逐条有结果证据（基线 §八 QA 义务） |

## 三、 打回机制（REJECTED）

1. **证据强制**：`rejection_history` 条目的 `evidence[]` 必须是物理路径或可定位的日志摘录，禁止"不完整""不合格"等空泛表述；每条未达标判据对应至少一项证据。
2. **打回粒度**：仅列未达标项与整改清单，已达标部分不要求重做；多任务关联失败时逐任务独立打回，不连坐。
3. **返工闭环**：`REJECTED → IN_PROGRESS` 由原作者认领；重新提测时 PM 按本轮 `round+1` 全量重验（不沿用上轮结论）。
4. **报警红线**：同一任务同一 `reason` 打回超过 2 次，PM 立即中断执行向用户报警（与 `state_machine.md` 一致）。
5. **下游保护**：被打回任务保持未 `ACCEPTED`，其全部下游依赖任务禁止派发；已派发的下游任务由 PM 置 `BLOCKED` 挂起。

## 四、 ACCEPTED 落账要求

- 全部判据通过后写入 `accepted_at`（UTC）；建议同时写 `verification_log` 一行摘要（核验时间 + 关键凭证路径）。
- 契约类交付物在任务 ACCEPTED 的同一轮完成 `contracts` 登记表落账（path/version/sha256/frozen_at），两者缺一不可——登记完成才算下游开工凭证生效。
