# 任务流转状态机

任务在 PM 与各成员角色之间的流转规则。本文件是 PM 流程总纲：状态流转、账本归属、门禁脚本口径、设计决策与团队文档清单。PM 独占状态流转，成员不读账本、不自行改状态。

## 状态枚举

| 状态 | 含义 |
| --- | --- |
| `TODO` | 已拆解，未派发/未开工 |
| `IN_PROGRESS` | 已派发，成员执行中 |
| `IN_REVIEW` | 成员汇报完成，PM 验收中 |
| `ACCEPTED` | 物理验收通过（终态） |
| `REJECTED` | 验收未通过，附原因与证据打回 |
| `BLOCKED` | 等待用户澄清或外部输入，挂起 |

## 流转定义

```
TODO → IN_PROGRESS → IN_REVIEW → ACCEPTED
IN_REVIEW → REJECTED（验收失败，附原因与打回证据）
REJECTED → IN_PROGRESS（原作者返工）
TODO / IN_PROGRESS → BLOCKED（等待用户澄清或外部输入），阻塞解除后恢复挂起前状态
```

| 流转 | 触发与责任 |
| --- | --- |
| `TODO → IN_PROGRESS` | PM 完成派发前置检查后派发，成员开工 |
| `IN_PROGRESS → IN_REVIEW` | 成员汇报完成，PM 置位并启动物理验收 |
| `IN_REVIEW → ACCEPTED` | PM 物理验收全部通过 |
| `IN_REVIEW → REJECTED` | 任一验收项未达标，附具体证据打回 |
| `REJECTED → IN_PROGRESS` | 原作者认领返工 |
| `→ BLOCKED → 原状态` | 等待用户决策/外部输入时挂起，解除后恢复 |

**派发前置检查**：任务 `inputs` 依赖的上游任务必须全部 `ACCEPTED`，契约类输入必须已在项目 `contracts` 登记表冻结，否则禁止派发。

## 单写者原则

`tasks.json` 仅由 PM 统一写入。成员只汇报进度与产出，严禁自行修改账本；所有状态流转由 PM 对账后落笔。

## 账本归属（R4，中央账本）

中央账本，路径 = 蓝图源仓库根下 `tasks.json`。否决的 R4-b（账本随项目）会让 `root_dir` 恒等于 "."，废掉隔离判据；账本放进插件目录更不可行——装机态版本递增即更换解析基准并丢弃记账历史。

- `{ledger}` 必须解析为仓库根 `tasks.json` 完整路径，由执行者一次性代入；裸写 `tasks.json` 属违规。
- `{ledger}` 禁止指向插件安装目录。开发态两者恰好同值，不构成混用理由。
- 所有读写账本的命令一律显式传 `--ledger "{ledger}"`，禁止依赖脚本默认值。
- `root_dir` 相对账本所在目录解析，可用 `../x` 或绝对路径指向仓库外工程；这是设计前提，不是路径逃逸。
- 账本进 git 版本库，记账历史即审计痕迹；并发冲突以 PM 单写者身份人工裁决后重放。
- 只装插件、未 clone 蓝图源仓库的机器无法运行 PM（`{ledger}` 无处解析）。

## 门禁脚本口径（R3）

门禁脚本一律写成 `bash skills/<skill>/scripts/<script>.sh "{root_dir}/<target>"`，路径相对本仓库根，agent 加载 skill 后可直接运行；脚本不复制进项目，项目内副本一律视为无效证据。

- 脚本路径统一用相对仓库根的 `skills/<skill>/scripts/xxx.sh`，不依赖任何需人工代入的「工具根」变量。
- 项目侧只允许 mvn / npm 等构建测试命令；`check_*.sh` 不进项目资产复制清单。
- 被验收方不得持有验收工具：门禁执行权在开发（自跑留证）与 PM/QA（重跑复核），复核那份与交付物物理分离。
- skill 自身回归保留 cwd = skill 目录的相对写法，那不是项目门禁。
- python 工具与 `requirements.txt` 同走 `skills/<tool>/`。
- 脚本默认值是 cwd 相对字面量，执行一律显式传项目参数（`{ledger}`、`{root_dir}`）。
- `actors.*.skills` 与 `skills/` 目录名是技能标识，供 Agent frontmatter 对齐。

## 打回记录与报警红线

每次打回必须在任务的 `rejection_history` 中追加一条记录：

```json
{
  "round": 1,
  "rejected_at": "2026-11-09T21:00:00Z",
  "reason": "单元测试通过率不足 100%",
  "evidence": ["tests/test_auth.py::test_login 失败日志的物理路径或摘录"]
}
```

同一问题同一原因打回超过 2 次（按 `reason` 计数），PM 立即中断执行并向用户报警求助。

## 变更纪律

先改权威文档，再改脚本与 skill，最后改角色 prompt 与判据。改门禁判据等同改流程，须总架构师确认；新增机检能力后才允许把对应 gate 的 `machine` 从 false 改 true，`machine` 字段的唯一依据是脚本真的会查。

## 已知缺口

- 无执行器：`workflow.yaml` 是 PM 手工执行的操作手册，不是程序；自动编排需读 yaml、按 gate 退出码路由的实现。
- PRD / Tech Spec 无内容校验器，节号与参数表靠人工对账。
- 追溯缺口：REQ-ID 不进任务卡字段，需求与任务、契约 operation 的对应只存在于交付报告。
- 契约 §八 声明无机检，G-SEC-DECL 与 G-REGISTER 之间存在人工空档。
- 并发写账本需 git 或锁文件裁决，方案未定。
- QA 用例覆盖率与安全用例族无法机器核验。
