# 需求澄清与定界模版（PRD）

实例落 `{root_dir}/docs/prd-v{N}.md`，由 PM 产出、总架构师（用户）确认后方可派发。它是全链路唯一的**业务事实来源**：architect 从它取实体关系与权限口径去出 Tech Spec 和契约，开发从它取验收口径，QA 从它取"什么算满足需求"。

- 权威分工：业务事实只在本文件；技术取值在 Tech Spec；条款在协议与 skill。本模版不复制任何技术条款。
- 填写约定：与 `Tech Spec 模版.md` 一致——`【填写】` 由 PM 落实；`【待确认】` 只能由总架构师答复后回填。**禁止用"通常做法""业界一般"填补用户没说过的需求**（PM prompt §1）。
- 节号是跨角色引用锚点：不适用的节保留标题写"本项目不涉及：{理由}"，禁止整节删除。
- 机检现状：本文件的内容质量**没有脚本校验**（`validate.py` / `lint.py` 都不读 PRD），靠 §十二 DoD + 附录 A/B 的人工对账。

## 一、元信息与版本

| 项 | 值 |
| --- | --- |
| 项目名 / `root_dir` | 【填写】 |
| 任务前缀 | 【填写，如 `AUTH`】 |
| PRD 版本 / 状态 | v{N} / 草案 · 待答复 · 已确认可派发 |
| 需求来源 | 【填写：用户原话所在讨论 / 外部文档路径】 |
| 编写 / 答复 / 确认 | PM 编写；歧义由总架构师答复；确认后进入拆解派发 |
| 下游制品 | Tech Spec 版本：【填写或"未产出"】；已冻结契约：见 `tasks.json` 项目 `contracts` 表（本文件不重复登记 sha256） |

- 任务前缀必须与账本一致：`task_id` 形如 `{前缀}-{三位序号}`（`task-schema.json`），且前缀跨项目唯一——`validate.py` 的 P006 会就冲突报 ERROR、与前缀与 `project_id` 无语义关联报 WARN。
- 版本递增规则见 §十一；`已确认可派发` 之后的任何内容变化都必须先开 Change Request。

## 二、业务目标与成功判据

| 项 | 内容 |
| --- | --- |
| 要解决的问题 | 【填写：现状是什么、痛在哪、谁在痛】 |
| 成功判据 | 【填写：可测的事实，如"某流程从 N 步降到 M 步""支撑 X 并发下的 Y 操作"】 |
| 基线数值 | 【填写：当前实测值与测量方法】 |

- 目标数值无来源时写 `【待确认】` 并进 §三.2 提问，**不得编一个数当需求**——QA 的功能断言与 §八 性能指标都要回指这里。

## 三、需求澄清台账

### 3.1 已明确业务事实

PM prompt §1 的第一栏。每条事实必须能指回用户说过的原话或既有制品，否则不能进本表。

| 编号 | 业务事实 | 来源 | 下游取用者 |
| --- | --- | --- | --- |
| FACT-1 | 【填写】 | 用户表述（附原话摘录或消息定位）/ 已交付文档路径 | architect / 开发 / QA |

### 3.2 待确认歧义与隐性约束

PM prompt §1 的第二栏。**命中下列六类之一就必须问，不得自行推定**：技术选型、接口协议、鉴权方式、数据持久化、安全合规参数（基线 §九留白项）、不可逆操作。

| 编号 | 问题 | 命中类别 | 影响面 | 不答复的后果 | 状态 |
| --- | --- | --- | --- | --- | --- |
| Q-1 | 【填写】 | 选型 / 协议 / 鉴权 / 持久化 / 基线留白 / 不可逆 | 【填写：受影响的需求编号】 | 【填写：哪一段无法拆解或无法验证】 | 待答 / 已答→写入 {节号或编号} / 已转 §五 待拍板 |

- 状态为 `待答` 的问题所关联的需求条目，**不得进 §六 拆解、不得派发**；相关任务卡由 PM 标 `BLOCKED` 挂起。
- 答复原文要留档：状态改 `已答` 时在备注写答复出处，避免后续对账失真。

## 四、角色与权限（业务口径）

只写业务语言"谁能做什么、看不到什么"，角色枚举值与权限点字符串由 architect 落进 Tech Spec §三 与契约 `x-roles` / `x-permissions`。

| 业务角色 | 能做什么 | 不能做什么 | 数据可见范围 | 备注 |
| --- | --- | --- | --- | --- |
| 【填写】 | 【填写】 | 【填写】 | 本租户 / 仅本人创建 / 全平台 / 公开 | 【填写】 |

- 是否存在跨租户可见的资源？【填写：有则逐个说明判定条件；无则写"无，全部按租户隔离"】——这条决定 Tech Spec §四 属主条件表能否填满，也决定 QA 水平越权用例是否有基准。
- 是否需要平台管理员与业务管理员职责分离？【填写】
- 账号从哪来（注册 / 后台开通 / 外部系统同步）？离职或停用后如何处理？【填写，对应基线 AC-3】

| D-1 | 口令复杂度与轮换周期 | 基线 §九.1 | 【填写】 | 【待拍板】 | Tech Spec §七 |
| D-2 | 登录失败锁定阈值与时长 | 基线 §九.2 | 【填写】 | 【待拍板】 | Tech Spec §七 |

## 六、需求条目（可原子拆解）

| REQ-ID | 用户可见行为 | 优先级 | 涉及端 | 验收口径（可判真伪） | 关联 FACT/Q | 粒度预估 |
| --- | --- | --- | --- | --- | --- | --- |
| REQ-001 | 【填写】 | P0 / P1 / P2 | 后端 / 前端 / 数据 | 【填写】 | FACT-1, Q-2 | S / M / L |

- **验收口径的写法**：一句能被证伪的事实。输入类写"提交 X 得到 Y，提交非法 Z 得到明确拒绝"；列表类写"分页参数越界时的表现"；不写接口路径与字段名（那是契约的事），也不写错误码数字（那是 architect 与后端的事）。
- 口径里出现"错误提示友好""响应快"这类无法判定的表述 = 澄清未闭环，退回 §三.2 提问。
- 粒度预估 `L` 的需求**不允许直接派发**，先二次拆解（PM prompt §2）；本表写的是需求条目的预估，任务卡的 `complexity` 只有 S / M。
- 需求条目与契约 operation 的对照由 architect 在交付报告给出，PRD 不维护接口清单。
- 每条 REQ 必须至少关联一个 FACT；找不到业务事实来源的需求，要么补澄清要么删掉。

## 九、范围之外（本期不做）

| 项 | 为何不做 | 归属 | 重提条件 |
| --- | --- | --- | --- |
| 【填写】 | 【填写：成本 / 依赖未到位 / 需求未澄清】 | 后续批次 / 其他系统 / 决定永久不做 | 【填写】 |

- 本表与各角色 prompt 的范围蠕变防护共用：开发中途发现的"顺手就能加"若命中本表，只能记录上报，不得就地实现。

## 十一、变更控制（Change Request）

| CR 编号 | 变更内容 | 触及节号 | 已冻结/已验收的影响 | 处置 |
| --- | --- | --- | --- | --- |
| CR-1 | 【填写】 | §六 REQ-xxx / §七 实体 / §八 指标 | 契约 v{n} 是否需重新校验冻结；已 `ACCEPTED` 任务是否需重开 | 新开 REQ / PRD 版本递增 / 走契约变更流程 |

- **禁止在当前批次内默许需求蠕变**（PM 红线 3）：口头新增的诉求先进本表，再决定是否进版本。
- 触及已冻结契约的变更一律按 `接口契约标准.md` §七 分级：`BREAKING_CHANGE` 须总架构师决策结论 + 新大版本文件，不得就地覆盖。
- 版本递增：新增/删除 REQ、改验收口径、改权限范围、改数据要求 → 大版本；纯澄清补充与措辞 → 小版本。§一 状态需相应回到"待确认"直到总架构师确认。
- PRD 新版本落地后，PM 同步通知 architect 复核 Tech Spec 是否受牵连（尤其 §三/§四/§五/§七）。

## 十二、PRD 通过条件（DoD）

全部满足才可派发 architect 与开发任务：

1. §一 任务前缀与账本一致且不与他项目冲突；状态为"已确认可派发"。
2. §二 成功判据可实测，无主观词。
3. §三.2 所有问题状态非 `待答`，或已按 §五 转为拍板项且相关 REQ 已标注降级口径。
4. §四 数据可见范围逐角色明确，跨租户特例已列举。
5. §五 基线 §九 六项逐条在表（涉及或写明不涉及），结论列非空或显式【待拍板】。
6. §六 每条 REQ 有可判真伪的验收口径、至少一个 FACT 支撑、粒度非 L。
7. §七 实体关系与量级填写完成；7.2 告知同意口径确认；7.3 不可逆操作已列举并给出可回滚性。
8. §八 数值有依据或标 `【待确认】` 且已进 §三.2。
9. §九 与 Tech Spec §十一 不做清单一致。
10. §十 每个阶段的前置门禁写明。

## 附录 A：PM 自检清单

- 我是否把某个问题用"一般系统都这么做"回答了？命中即退回提问。
- §六 的验收口径能不能被 QA 直接变成断言？不能就重写。
- §五 是否只在 PRD 里记了结论、没有写死阈值数字（数字归 Tech Spec）。
- 变更是否走了 §十一，而不是在当前版本原地改写已确认内容。
- PRD 版本、Tech Spec 版本、契约版本三者时间线是否自洽（下游版本不早于上游）。

## 附录 B：architect 接收检查

进入 Tech Spec / 契约编写前逐条确认，缺项即打回 PM，不带缺口设计：

1. §四 权限口径足以定义 `x-roles` 与权限点；§七.1 实体关系足以推导表与关联。
2. §五 与需求相关的拍板项已有结论或已明确留白范围（留白项在 Tech Spec §七 原样登记，不自行填数）。
3. §六 每条 REQ 的验收口径可映射到契约行为（成功响应 / 错误分支），且未越界规定接口路径与字段名。
4. §七.2 敏感采集字段齐备，可直接转成 `x-sensitive` / `writeOnly` 标注与存储形态决策。
5. §八 审计与运维诉求足以确定审计落点与检索维度。
