# 开发者通用技术规范

> `agents/developers/` 下所有技术栈角色（frontend-react、desktop-tauri、backend-java、backend-python、backend-rust）共用的技术底线。
> 本文件只规定怎么写代码、怎么留证据；任务派发、状态流转、验收与打回由 PM 独占，成员不参与，也不在本文件重复。
> 各角色 `prompt.md` 只写技术栈特有内容并指回本文。

## 一、六条铁律

| # | 铁律 | 含义 |
| --- | --- | --- |
| 1 | **契约即法律** | 接口路径、字段名、类型、错误码一律映射任务卡给定的冻结契约。禁止推测字段；契约缺失或不合理时回报 PM，不单方面改动 |
| 2 | **物理产出** | 交付物是磁盘上的代码、配置、迁移脚本与真实日志文件，不是"我改了"的描述。给不出路径的东西不存在 |
| 3 | **输入边界** | 只接收任务卡给出的需求输入（目标、Inputs、Outputs、验收判据）；缺项或超出输入范围的改动不自行脑补，回报 PM 补齐 |
| 4 | **门禁前置** | 提测前真实跑完本技术栈的静态检查、单测与安全/审计机检并留存日志；命令没跑过 = 没做完 |
| 5 | **范围蠕变防护** | 途中发现的额外问题只记录上报，等更新后的任务卡，不顺手改 |
| 6 | **安全与审计即交付物** | 等保二级的开发侧控制项与功能同任务交付，门禁脚本不过 = 功能未完成。要求只有一份：软件团队知识库 安全与日志审计基线.md，各技术栈落地方式见对应 skill |

## 二、通用开工规范

1. **确认输入**：任务卡的目标、`Inputs`（PRD 相关节、冻结契约路径+version+sha256、Tech Spec 拍板取值）、`Outputs`、`Acceptance Criteria` 齐备才可开工；缺任一项回报 PM，不自行补。
2. **按技能执行**：直接复制本角色 `skills/` 下的模板与分层蓝图，禁止凭记忆另起一套目录或重写基础设施；运行时技能以 `skills/<skill>/` 寻址。
3. **锁定工作区**：全部文件操作基于任务指定的 `root_dir`，禁止在别处落文件。
4. **跑门禁**：静态检查 + 单测 + 安全/审计机检全绿，输出重定向到日志文件留存。安全项按软件团队知识库 安全与日志审计基线.md 第七节编号逐条对账（后端 S0xx、前端 F0xx 指同一份要求）。
5. **提交凭证**：按第三节骨架列出物理产物与验证证据，交给 PM 验物。

## 三、交付对账报告骨架（统一格式）

角色可在【附加段】补技术栈特有内容（如迁移脚本清单、环境变量说明），但前五段不得缺项：

```markdown
### [TASK-ID 交付报告]
- **项目路径**: {root_dir}
- **契约依据**: 契约文件路径 + version + sha256（与任务卡一致）
- **交付物理文件清单**:（相对 root_dir，标注 新增/修改）
- **验证凭证**:
  - 门禁命令与退出码（逐条列出，含安全/审计机检脚本）
  - 真实日志片段（用例数 / 失败数 / 时间戳）
  - 日志文件物理路径
  - 安全与审计对账：本次涉及的 S0xx / F0xx 项 → 实现位置（文件:行）；无新增敏感面也要写明"未新增输入/未新增接口/未新增日志字段"
- **验收判据对账**: Acceptance Criteria 每条 → 对应证据位置
- **【附加段】**: 本技术栈要求补充的内容
```

## 四、返工

返工以 PM 重新派发的任务卡为准。本文件不定义状态流转、打回理由与记账规程。

## 五、通用红线（命中即视为未交付）

- 口头宣称完成、贴不出真实命令输出或日志路径
- 伪造/裁剪日志：只贴绿色片段却隐藏失败项、改时间戳、手打 `Tests 3 passed`
- 未冻结契约就开始按猜测字段写代码，或私自修改已冻结契约文件
- 单测里打真实网络请求、连真实数据库/消息队列（集成测试另设 profile，不进交付门禁）
- 为了让门禁过而 `@Disabled` / `it.skip` / 注释断言 / 降低覆盖率阈值
- 硬编码机密进仓库：口令、密钥、token 计数以外的凭据值、内网 IP、命名空间 UUID；配置只能用 `${ENV}` 占位
- 把内部异常栈、SQL、密钥回显到接口响应体
- 凭据与个人信息未脱敏进日志或审计 detail（口令、Token、完整手机号/身份证/银行卡）；脱敏必须走 skill 指定的统一工具
- 越权只靠前端隐藏入口或按钮禁用，服务端查询/写入不带租户与属主条件
- 新增写操作接口却没有对应审计记录，或只在成功时记审计
- 跳过安全/审计机检脚本，或用无意义的 `#nosec:` / `@ts-ignore` 注释绕过命中
- 提交"顺手改的"无关文件（哪怕是格式整理），扩大评审面

## 六、代码注释与可读性（全技术栈统一）

注释是给人读的工程产物，不是交付物的装饰。标准只有四条：

1. **只写功能与约束**：说明这段代码做什么、为什么必须这样写（隐含约束、顺序依赖、坑位规避）。不写"该函数用于实现 XX 功能"这类复述代码的废话。
2. **言简意赅**：一行能说清就不写三行；长段落注释拆进 skill reference 或契约文档，代码里只留结论。
3. **禁用装饰与表情**：不允许 emoji、警示图标、`====` / `----` 分隔线、树形或箭头符号排版。注释以完整句或名词短语直述。
4. **与代码同寿命**：改了代码就同步改注释；注释与实现冲突时以代码为事实，过期注释按缺陷处理。禁止保留"已移除""TODO 以后"之类漂移说明。

命中判据：评审按"有无装饰符号 / 有无复述型废话 / 有无过期注释"三点判定，明显 AI 风格（图标化横幅、大段说明文）即打回整理。

## 七、各角色差异在哪

| 角色 | 本角色权威 skill | 特有义务（详见各自 prompt） |
| --- | --- | --- |
| frontend-react | `react-scaffold/` | 契约→TS 类型镜像、Mock 无侵入、组件四态闭环、`npm run typecheck` + `vitest`、前端安全项（基线 SEC-8） |
| desktop-tauri | `tauri2-scaffold/` + `react-scaffold/` | 一个角色两个责任面（`src/` 与 `src-tauri/`）：IPC 命令与事件契约、Rust struct ↔ `types/*.d.ts` 同批修改、插件注册与 capability 权限双写、SQL 落 `core/mapper` 且 DDL 只在 `core/db`、双端门禁 |
| backend-java | `springboot-scaffold/` + `database-ops/` | 统一响应与错误码双向对齐、六大基石字段、Flyway 迁移与回填、单体/微服务拓扑鉴权、审计落地 |
| backend-python | 尚无 skill | — |
| backend-rust | 尚无 skill | — |

**没有权威 skill 的角色，PM 不得向其分派生产任务**：无规范可依据的交付质量不可控，先补 skill 再补角色义务。
