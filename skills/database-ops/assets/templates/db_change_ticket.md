## 二、变更内容与依据

- 脚本清单：`V{n}__xxx.sql`（每个版本号做了什么，一句话）
- 表结构设计依据：新增列/索引对应的**真实查询**是什么，贴 `WHERE`/`ORDER BY` 片段
- 执行计划取证：`EXPLAIN (ANALYZE, BUFFERS)` 或 `EXPLAIN ANALYZE` 摘要（走了哪个索引、估算与实际行数、是否落盘排序）
- 数据量与增速：当前行数 / 单行平均宽度 / 一年后预估（决定是否分区或归档）

## 三、风险评估

| 项 | 结论 |
| --- | --- |
| 预估影响行数 | 预查 `SELECT COUNT(*)` 的实际输出，不许写"大概" |
| 锁与阻塞 | 持锁类型与时长；是否 `ACCESS EXCLUSIVE`；大表 DDL 用哪种在线算法（`CONCURRENTLY` / `ALGORITHM=INPLACE, LOCK=NONE` / `INSTANT`） |
| 预估耗时 | 在接近生产数据量的副本上实测的耗时 |
| 执行窗口 | 时段 + 该时段 QPS/连接水位（避开批处理与高峰） |
| 事务边界 | 是否含 `CREATE INDEX CONCURRENTLY`（不能在事务内）；MySQL 是否已按"一脚本一 DDL"拆分 |
| 回滚可行性 | 可逆（有 U 脚本）/ 不可逆（依赖备份恢复），不可逆必须写恢复耗时 |
| 下游影响 | 从库、CDC/binlog 订阅、数仓抽表、搜索引擎同步，是否已通知并确认 |
