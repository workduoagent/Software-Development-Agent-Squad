# 项目内规范目录与 AI 工作记忆

桌面工程起步时要落地两套资产，别混为一谈：

| | `.workspace/.norms/` | `.workbuddy/memory/` |
| --- | --- | --- |
| 性质 | **规范**（纪律） | **记忆**（现状） |
| 回答 | 「代码该怎么写」 | 「这个项目实际长什么样」 |
| 内容 | 通用规则、红线、自检清单 | 技术栈实况、目录差异、踩过的坑、命令 |
| 面向 | 团队全体 + 所有 AI 会话 | AI 跨会话接手时的上下文 |
| 是否入库 | ✅ **必须进版本库** | ⚪ 通常忽略（各人记忆不同） |
| 冲突时 | 与代码冲突 → **先改规范再改代码** | 与规范冲突 → 以规范为准，同步更新记忆 |

一句话：**规范管「必须怎么做」，记忆管「这里实际是什么」**。

## 一、为什么要有规范目录

| 问题 | 规范的解法 |
| --- | --- |
| AI 每次生成风格不一致 | 布局、命名、依赖、验证命令全部写死成硬规则 |
| 「改代码还是改规范」扯皮 | 总则第 0 条定死：先改规范再改代码 |
| 反复犯同样的错 | 把踩过的坑写进规范 |
| 新人/新会话快速上手 | 只需读 `.norms/` 四份文件，不用读全部代码 |

## 二、`.norms/README.md` 总则

```markdown
# .norms —— 开发与协作规范

> 编码工具（AI / 人）在仓库内干活前必读本目录；
> 规范与代码冲突时，先改规范再改代码（规范也要走提交）。

| 文件 | 范围 |
|---|---|
| frontend.md | 前端开发规范 |
| backend.md | 后端开发规范 |
| git-commit.md | 提交协作规范 |

## 通用总则（前后端共同）

0. **先改规范再改代码**——规范冲突时以规范为准，规范过时则先更新规范。
1. **事实源优先**：能力可用性以注册表/类型定义为准，禁止只靠 prompt「宣称能做」。
2. **注释只写 WHY**：约束、反直觉、workaround；禁止叙述型注释。
3. **契约先行**：接口/事件/命令变更先改契约文档与类型，再改实现；事件只增不改。
4. **依赖入清单**：只在 `package.json` / `Cargo.toml` 增依赖；大依赖需说明理由。
5. **密钥红线**：密钥不进代码、不进聊天记录、不进提交。
6. **完成定义**：对应检查命令 0 error（前端 typecheck，后端 cargo check）。
7. **死代码即删**：确认无用就删，不留兼容空壳。
```

`frontend.md` / `backend.md` 的内容分别见 `frontend-shell.md` §5–§7 与 `rust-backend.md` §3–§6，直接摘录即可，不在项目里另写一套。

## 三、`.norms/git-commit.md` 提交协作规范

```markdown
# 提交协作规范（编码工具 × 用户）

> 核心约定：编码工具负责改代码、写 commit 信息、执行 commit；
> push 一律由用户本人完成。

## 分工
| 动作 | 谁 |
|---|---|
| 改代码 / 自检 | 编码工具（typecheck / cargo check 先过） |
| 写 commit 信息 | 编码工具 |
| git commit | 编码工具（只提交本次相关文件） |
| git push | 用户本人（工具永不执行） |

## 提交纪律
1. **范围圈定**：只提交本次工作文件；用户自己的遗留改动不混入。
2. **先自检后提交**：前端过 typecheck，后端过 cargo check。
3. **不碰**：密钥/.env、二进制、node_modules、他人未提交改动。
4. 未跟踪文件先 git add 再提交。

## Commit 信息风格
    <type>(<scope>): <中文主题——一句话说清做了什么>

    - 要点 1（改了什么、为什么）
    - 要点 2
    - 验证：过了哪些检查

- type：feat / fix / refactor / chore / docs / test
- scope 用模块短名；验证结论必须写；一个语义一个提交

## 红线
- 禁止 git reset --hard 到远端未同步状态、禁止改写已推送历史。
- 提交后报告：commit hash + 主题 + 「可以推送了」；遗留未提交改动逐项列明归属。
```

⚠️ **与本小分队既有纪律的差异，需总架构师拍板**：小分队现行口径是「未获明确指示，任何角色不得执行 git 操作（含 commit）」，而上面这份模板授权工具自行 commit。两者不可同时生效——落地前必须在项目 `.norms/` 与本仓库之间选一个口径，否则同一个角色在两个工程里行为不一致。建议：项目内按 `.norms/` 执行，但**每次任务卡显式声明 `git_policy: allow-commit`** 才生效，缺声明即回到"只改不提交"。

## 四、`.workbuddy/memory/` AI 工作记忆

两层结构：

| 文件 | 性质 | 写什么 | 维护方式 |
| --- | --- | --- | --- |
| `MEMORY.md` | 长期约定（单一来源） | 项目技术栈、目录约定、命令、踩过的坑、协作模式 | 原地更新，保持精简（≤6KB） |
| `YYYY-MM-DD.md` | 每日日志（追加式） | 当天做了什么、为什么、验证结果 | 只追加，永不覆盖 |

分工原则：**约定进 MEMORY，过程进日志**。

`MEMORY.md` 骨架：技术栈 / 目录约定 / 常用命令 / 已踩过的坑 / 协作约定 五节，超过 6KB 说明写多了，把过程性内容挪进每日日志。

写入纪律：

| 时机 | 动作 |
| --- | --- |
| 完成任务后 | 向当日日志**追加**一段（带 commit hash） |
| 发现新约定/新坑 | 更新 `MEMORY.md`（原地改，保持精简） |
| 仅查资料、简单问答 | **不写**记忆 |
| 超过 30 天的日志 | 提炼进 `MEMORY.md` 后删除，保持目录干净 |

不记流水账：只记「有决策含量」的事。搜索结果、临时路径、工具报错不用记。

## 五、`.gitignore` 配置

规范必须进仓库——它是团队和 AI 的共享契约，不进版本库等于不存在：

```gitignore
.workspace/*
!.workspace/.norms/
!.workspace/.norms/**
.workbuddy/
```

若希望记忆随仓库共享，反向配置 `.workbuddy/*` + `!.workbuddy/memory/`。建议先按个人模式（忽略）起步；等 `MEMORY.md` 里沉淀出真正的团队约定，再把那部分内容提升进 `.workspace/.norms/`（规范进库、记忆不入库）。
