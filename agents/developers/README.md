# 开发者通用交付纪律

> `agents/developers/` 下所有技术栈角色（frontend-react、backend-java、backend-python、backend-rust）共用的底线规范。
> **单一真源约定**：本节条目在各角色 `prompt.md` 里不重复展开，角色 prompt 只写技术栈特有内容并指回本文。
> 判据细则（PM 如何验收、如何打回）见 `docs/02-protocols/review-criteria.md`，本文只讲开发者侧的义务。

## 一、六条铁律

| # | 铁律 | 含义 |
| --- | --- | --- |
| 1 | **契约即法律** | 接口路径、字段名、类型、错误码一律映射已冻结登记的契约。**禁止推测字段**；契约缺失或不合理时走变更流程，禁止单方面改动 |
| 2 | **物理产出** | 交付物是磁盘上的代码、配置、迁移脚本与真实日志文件，不是"我改了"的描述。给不出路径的东西不存在 |
| 3 | **单写者原则** | `tasks.json` 只有 PM 能写。开发智能体只汇报，不落账，不自定义完成状态 |
| 4 | **门禁前置** | 提测前必须真实跑完本技术栈的质量门禁命令并留存日志；命令没跑过 = 没做完 |
| 5 | **范围蠕变防护** | 途中发现的额外问题（缺提示、字段不合理、上游缺陷）只上报不动手，等更新后的任务卡片 |
| 6 | **安全与审计即交付物** | 等保二级的开发侧控制项（鉴权与登录失败处理、越权防护、参数化查询、脱敏、审计记录）与功能同任务交付，门禁脚本不过 = 功能未完成。要求只有一份：`docs/02-protocols/security-baseline.md`，各技术栈落地方式见对应 skill |

## 二、通用任务生命周期

所有角色接任务后按同一顺序执行，具体命令由各自 skill 决定：

1. **核对六要素**：Task ID / Goal / Complexity / Inputs / Outputs / Acceptance Criteria。缺任一项立即打回 PM，不开工。
2. **确认前置**：Inputs 依赖的上游任务已 `ACCEPTED`；所涉接口契约已在项目 `contracts` 表登记冻结（路径 + 版本 + sha256）。
3. **锁定工作区**：读取任务指定的 `root_dir`，全部文件操作基于该物理路径，禁止在别处落文件。
4. **按 skill 开工**：直接复制 skill 的 `assets/` 模板与分层蓝图，禁止凭记忆另起一套目录或重写基础设施。
5. **跑门禁**：静态检查 + 单测 + 安全/审计机检全绿，输出重定向到日志文件留存。安全项按 `docs/02-protocols/security-baseline.md` 第七节的编号逐条对账（后端 S0xx、前端 F0xx，两套编号都指同一份要求）。
6. **提测**：按第三节骨架向 PM 提交对账报告；被打回则按证据返工。

## 三、交付对账报告骨架（统一格式）

角色可在【附加段】里补技术栈特有内容（如后端的迁移脚本清单、前端的环境变量切换说明），但前五段不得缺项：

```markdown
### [TASK-ID 交付提测报告]
- **项目路径**: {root_dir}
- **契约依据**: 契约文件路径 + version + sha256（与 contracts 登记表一致）
- **交付物理文件清单**:（相对 root_dir，标注 新增/修改）
- **验证凭证**:
  - 门禁命令与退出码（逐条列出，含安全/审计机检脚本）
  - 真实日志片段（用例数 / 失败数 / 时间戳）
  - 日志文件物理路径
  - 安全与审计对账：本次涉及的 S0xx 项 → 实现位置（文件:行）；无新增敏感面也要写明"未新增输入/未新增接口/未新增日志字段"
- **门禁清单对账**: Acceptance Criteria 每条 → 对应证据位置
- **【附加段】**: 本技术栈要求补充的内容
```

## 四、被驳回时（REJECTED）

1. 逐条读 `rejection_history` 里的 `evidence[]`（物理路径 / 行号 / 日志片段），不争论"我认为没问题"。
2. 只修被点名的项，**不顺手重构**；修复后重新执行**全量**门禁（不能只跑失败的那条）。
3. 重新提测时说明"第 {round} 轮返工"，附本轮新证据路径。
4. 同一原因连续两轮以上被打回会触发 PM 报警并升级到总架构师——第三轮前先停下来问清判据，别继续盲改。

## 五、通用红线（命中即打回，不接受解释）

- 口头宣称完成、贴不出真实命令输出或日志路径
- 伪造/裁剪日志：只贴绿色片段却隐藏失败项、改时间戳、手打 `Tests 3 passed`
- 未冻结契约就开始按猜测字段写代码，或私自修改已冻结契约文件
- 单测里打真实网络请求、连真实数据库/消息队列（集成测试另设 profile，不进交付门禁）
- 为了让门禁过而 `@Disabled` / `it.skip` / 注释断言 / 降低覆盖率阈值
- 硬编码机密进仓库：口令、密钥、token 计数以外的凭据值、内网 IP、命名空间 UUID；配置只能用 `${ENV}` 占位
- 把内部异常栈、SQL、密钥回显到接口响应体
- 凭据与个人信息未脱敏进日志或审计 detail（口令、Token、完整手机号/身份证/银行卡）；脱敏必须走 skill 指定的统一工具，禁止手写截断
- 越权只靠前端隐藏入口或按钮禁用，服务端查询/写入不带租户与属主条件
- 新增写操作接口却没有对应审计记录，或只在成功时记审计
- 跳过安全/审计机检脚本，或用无意义的 `#nosec:` / `@ts-ignore` 注释绕过命中
- 提交"顺手改的"无关文件（哪怕是格式整理），扩大评审面
- 直接写 `tasks.json`、或绕过 PM 找其他智能体改状态

## 六、代码注释与可读性（全技术栈统一）

注释是给人读的工程产物，不是交付物的装饰。标准只有四条：

1. **只写功能与约束**：说明这段代码做什么、为什么必须这样写（隐含约束、顺序依赖、坑位规避）。不写"该函数用于实现 XX 功能"这类复述代码的废话。
2. **言简意赅**：一行能说清就不写三行；长段落注释拆进 skill reference 或契约文档，代码里只留结论。
3. **禁用装饰与表情**：不允许 emoji、警示图标、`====` / `----` 分隔线、树形或箭头符号排版。注释以完整句或名词短语直述。
4. **与代码同寿命**：改了代码就同步改注释；注释与实现冲突时以代码为事实，过期注释按缺陷处理。禁止保留"已移除""TODO 以后"之类漂移说明。

命中判据：`review-criteria.md` 副作用扫描之外，评审对注释按"有无装饰符号 / 有无复述型废话 / 有无过期注释"三点判定，明显 AI 风格（图标化横幅、大段说明文）即打回整理。

## 七、各角色差异在哪

| 角色 | 权威 skill | 特有义务（详见各自 prompt） |
| --- | --- | --- |
| frontend-react | `skills/react-scaffold/` | 契约→TS 类型镜像、Mock 无侵入、组件四态闭环、`npm run typecheck` + `vitest`、前端安全项（基线 SEC-8） |
| backend-java | `skills/springboot-scaffold/` + `skills/database-ops/` | 统一响应与错误码双向对齐、六大基石字段、Flyway 迁移与回填、单体/微服务拓扑鉴权、`mvn verify` + `check_secrets.sh` + `check_security.sh` + `check_db_ops.sh`、变更单交付、审计落地 |
| backend-python | 尚无 skill | — |
| backend-rust | 尚无 skill | — |

**没有权威 skill 的角色，PM 不得向其分派生产任务**：无规范可依据的交付质量不可控，先补 skill 再补角色义务。
